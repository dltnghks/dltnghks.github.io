# NoSQL(비관계형)

> [!summary] 한 줄 요약
> NoSQL은 관계형 테이블 모델 이외의 데이터 모델을 사용하는 저장소의 묶음으로, 데이터와 접근 패턴에 맞춰 유연한 구조·대규모 분산·빠른 특정 조회를 선택할 수 있게 한다.

## 1. NoSQL이 등장한 배경

웹 서비스가 커지면서 데이터 양, 요청 수, 데이터 형태가 빠르게 늘어났다. 모든 문제를 복잡한 조인과 고정된 테이블 구조로 풀기보다, 특정 접근 패턴에 맞는 저장 모델과 여러 서버로 나누기 쉬운 구조를 선택하려는 요구가 커졌다.

NoSQL은 보통 “Not Only SQL”로 해석한다. 즉 SQL이나 관계형 DB를 부정한다기보다, 관계형 모델 **이외의 선택지**를 함께 사용한다는 뜻에 가깝다.

```text
데이터 특성·조회 패턴·확장 요구 분석
→ 적합한 데이터 모델 선택
→ 필요한 정합성·트랜잭션 범위 결정
→ 분산·복제·장애 복구 방식 설계
```

## 2. 네 가지 대표 데이터 모델

NoSQL은 하나의 구조가 아니라 여러 데이터 모델의 묶음이다.

|모델|저장 단위|잘 맞는 접근 패턴|대표 제품 예시|
|---|---|---|---|
|키-값(Key-Value)|키와 값 한 쌍|키로 매우 빠르게 읽고 쓴다.|Redis, DynamoDB|
|문서(Document)|중첩 구조를 가진 문서|한 대상의 속성을 함께 읽고 구조가 자주 달라진다.|MongoDB|
|와이드 컬럼(Wide-Column)|행 키와 컬럼 묶음|대량의 쓰기와 특정 키·범위 중심 조회|Cassandra, HBase|
|그래프(Graph)|정점과 간선|사람·상품·관계의 여러 단계 연결을 탐색한다.|Neo4j|

### 키-값 모델

키 하나로 값을 바로 찾는 구조다. 로그인 세션, 캐시, 짧은 만료 시간이 있는 토큰처럼 “이 키의 현재 값”을 빠르게 다루는 데 적합하다.

```text
"session:abc123" → { user_id: 101, expires_at: ... }
```

### 문서 모델

문서는 JSON과 비슷한 중첩 구조로 한 대상을 표현한다. 상품마다 옵션이 다르거나, 사용자 프로필처럼 관련 속성을 한 번에 읽는 경우에 자연스럽다.

```text
상품 문서
{ id, 이름, 가격, 옵션: { 색상, 용량 }, 태그: [...] }
```

### 와이드 컬럼 모델

대량의 데이터를 여러 노드에 분산하고, 미리 정한 파티션 키와 조회 방식에 따라 빠르게 읽고 쓰는 데 초점을 둔다. 임의의 조인이나 모든 조건 조합을 즉석에서 지원하기보다, 핵심 질의를 기준으로 데이터를 모델링하는 경향이 강하다.

### 그래프 모델

정점(Node)과 간선(Edge)으로 사람, 상품, 장소 같은 대상과 그 관계를 직접 표현한다. “친구의 친구”, “이 사용자가 본 상품과 비슷한 상품”처럼 여러 단계 관계를 탐색하는 문제에 적합하다.

## 3. 스키마 유연성의 의미

NoSQL을 “스키마가 없다”라고 말하기 쉽지만, 정확히는 **DB가 모든 레코드에 같은 고정 구조를 강제하지 않을 수 있다**는 뜻이다. 애플리케이션, 검증 규칙, 문서 검증 기능에는 여전히 데이터 형식과 규칙이 필요하다.

|상황|관계형 모델|문서 모델의 한 예|
|---|---|---|
|셔츠 상품|공통 열과 별도 테이블로 색상·사이즈 표현|`색상`, `사이즈` 배열을 문서 안에 포함|
|노트북 상품|공통 열과 별도 테이블로 CPU·RAM 표현|`CPU`, `RAM` 속성을 같은 문서에 포함|

문서 구조가 유연하면 초기 개발과 속성 변화는 편할 수 있지만, 형식이 제각각으로 퍼지면 검색·검증·분석이 어려워질 수 있다. 따라서 어떤 속성은 필수인지, 변경은 어떻게 버전 관리할지를 정해야 한다.

## 4. 정합성과 분산

대규모 시스템은 데이터를 여러 노드에 **복제(Replication)** 하거나 **분할(Partitioning/Sharding)** 해 저장할 수 있다. 이때 한 노드의 변경이 모든 복제본에 즉시 보이지 않을 수 있고, 네트워크 장애 상황에서 어떤 보장을 우선할지 설계해야 한다.

|고려할 점|질문|
|---|---|
|일관성|쓰기 직후 모든 사용자가 같은 값을 반드시 봐야 하는가?|
|가용성|일부 노드·네트워크가 실패해도 요청에 응답해야 하는가?|
|지연 시간|사용자와 가까운 여러 지역에서 빠르게 응답해야 하는가?|
|트랜잭션 범위|한 문서·파티션이면 충분한가, 여러 데이터의 원자적 변경이 필요한가?|

> [!warning] NoSQL = 약한 정합성은 아니다
> 제품·설정·질의 방식에 따라 강한 일관성 읽기, 조건부 쓰기, 단일 문서 또는 여러 문서 트랜잭션을 제공할 수 있다. 반대로 관계형 DB도 복제 지연을 가진 읽기 복제본을 운영할 수 있다. 필요한 보장을 용어가 아니라 실제 연산과 배포 구조 단위로 확인해야 한다.

## 5. 언제 선택할까

다음과 같은 상황에서는 NoSQL 모델을 검토할 수 있다.

- 세션, 캐시, 순위표처럼 키 기반의 매우 빠른 읽기·쓰기가 중요하다.
- 사용자·상품처럼 항목별 속성의 차이가 크고, 한 대상의 정보를 통째로 읽는 일이 많다.
- 로그·이벤트·시계열 데이터처럼 대량 쓰기와 수평 확장이 핵심이다.
- 소셜 관계·추천 경로처럼 다단계 연결 탐색이 핵심이다.
- 데이터가 여러 지역·노드에 분산되어야 하고, 허용 가능한 일관성 수준을 명확히 설계할 수 있다.

그렇다고 해서 기존 관계형 DB를 바로 대체할 필요는 없다. 강한 참조 무결성, 복잡한 조인, 보고용 집계, 여러 엔티티를 아우르는 트랜잭션이 핵심이라면 [[RDBMS(관계형)]]이 더 단순하고 안전한 선택일 수 있다.

## 6. 자주 생기는 오해

### “NoSQL은 정형화되지 않은 데이터만 저장한다”

NoSQL도 키, 문서 필드, 그래프 스키마, 파티션 키처럼 구조를 가진다. 데이터 형태가 유연할 수 있다는 것과 데이터 모델이 전혀 없다는 것은 다르다.

### “NoSQL은 관계를 표현할 수 없다”

문서 안에 관련 데이터를 함께 넣거나 참조 키를 저장할 수 있고, 그래프 DB는 관계 자체를 핵심 모델로 삼는다. 다만 여러 엔티티를 임의로 조인하는 방식과 비용은 관계형 DB와 다를 수 있다.

### “규모가 커지면 무조건 NoSQL이 필요하다”

RDBMS도 인덱스, 캐시, 읽기 복제, 파티셔닝, 샤딩 등으로 규모를 키울 수 있다. 저장소 변경은 데이터 모델·운영·개발 복잡도까지 바꾸므로, 병목과 요구 사항을 측정한 뒤 결정해야 한다.

## 다음으로

저장 모델을 비교했다면, 실제 서비스에서는 데이터별 접근 패턴과 정합성 요구를 표로 정리한 뒤 관계형 DB와 NoSQL을 조합하는 방식을 설계한다.
