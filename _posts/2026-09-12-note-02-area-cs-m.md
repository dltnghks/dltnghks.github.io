# 데이터베이스 기초

> [!summary] 한 줄 요약
> DBMS는 데이터의 구조와 규칙을 관리하고, 트랜잭션과 ACID는 여러 변경이 실패·동시 실행 상황에서도 신뢰할 수 있게 끝나도록 돕는다.

## 1. 데이터베이스와 DBMS

- **데이터베이스(DB)**: 프로그램이 사용할 데이터를 구조적으로 보관한 집합이다.
- **DBMS**: DB를 만들고, 질의하고, 변경하고, 접근 권한·동시성·장애 복구를 관리하는 시스템이다.

애플리케이션은 파일의 특정 바이트를 직접 해석하는 대신, DBMS에 “이 조건에 맞는 주문을 찾아라” 또는 “재고를 1만큼 줄여라”라고 요청한다. DBMS는 저장 구조와 인덱스, 제약 조건, 동시성 제어를 사용해 요청을 처리한다.

|DBMS가 주로 맡는 일|의미|
|---|---|
|데이터 정의|테이블·문서 등 데이터 구조와 형식을 정한다.|
|데이터 조작|삽입, 조회, 수정, 삭제 요청을 처리한다.|
|무결성 유지|유효하지 않은 값이나 끊어진 참조를 막는다.|
|동시성 제어|여러 요청이 동시에 변경해도 결과가 꼬이지 않게 조정한다.|
|복구와 지속성|장애 뒤에도 확정된 변경을 복구한다.|
|보안|인증·권한으로 접근 범위를 제한한다.|

## 2. 엔티티, 속성, 레코드

업무에서 관리할 대상을 **엔티티(Entity)** 라고 한다. 쇼핑몰이라면 회원, 상품, 주문이 엔티티가 될 수 있다.

```text
회원(Entity)
├─ 회원 번호, 이름, 이메일 (속성, Attribute)
└─ (101, "민지", "minji@example.com") (한 건의 데이터, Record)
```

|용어|의미|관계형 DB에서 흔한 표현|
|---|---|---|
|엔티티|관리할 대상의 종류|테이블|
|속성|엔티티가 지닌 정보|열(Column)|
|레코드|한 대상에 대한 실제 데이터 한 건|행(Row)|
|식별자|각 대상을 구별하는 값|기본 키(Primary Key)|

엔티티는 현실 세계 자체가 아니라, 프로그램이 필요로 하는 관점으로 현실을 모델링한 것이다. 예를 들어 “회원 주소”는 한 개의 단순 속성일 수도 있고, 여러 배송지를 따로 관리해야 한다면 별도 엔티티가 될 수도 있다.

## 3. 스키마와 제약 조건

**스키마(Schema)** 는 데이터가 어떤 구조와 규칙을 가져야 하는지 정의한 설계도다. 반면 실제로 저장된 현재 데이터는 스키마에 따라 달라지는 **인스턴스(Instance)** 로 볼 수 있다.

|구분|예시|
|---|---|
|스키마|`주문`은 주문 번호, 회원 번호, 주문 시각, 상태를 가진다.|
|인스턴스|`(주문 5001, 회원 101, 2026-09-12, 결제완료)` 한 건이 저장되어 있다.|

스키마에는 값의 형태뿐 아니라 잘못된 상태를 막는 **제약 조건(Constraint)** 도 들어간다.

- 주문 번호는 중복되지 않아야 한다.
- 주문의 회원 번호는 존재하는 회원을 가리켜야 한다.
- 재고 수량은 음수가 될 수 없다.
- 주문 상태는 미리 정한 값 중 하나여야 한다.

> [!warning] 스키마가 곧 코드만으로 정해지는 것은 아니다
> 애플리케이션 코드에도 검증 로직을 둘 수 있지만, 여러 프로그램이 같은 데이터를 쓰거나 코드에 버그가 있을 수 있다. 중요한 규칙은 가능한 한 DB의 제약 조건에도 표현해 데이터 가까이에서 지키는 것이 안전하다.

## 4. 트랜잭션

**트랜잭션(Transaction)** 은 데이터베이스에 대한 하나 이상의 읽기·변경을 하나의 업무 단위로 묶은 것이다. 트랜잭션은 일반적으로 **커밋(Commit)** 으로 확정하거나, 문제가 생기면 **롤백(Rollback)** 으로 취소한다.

```text
트랜잭션 시작
→ 필요한 데이터를 읽고 검증
→ 여러 데이터 변경
→ 모두 조건을 만족하면 커밋
→ 오류·충돌·취소가 나면 롤백
```

예를 들어 계좌 이체는 출금과 입금이 둘 다 성공해야 한다. 출금만 반영된 뒤 서버가 멈추면 돈이 사라진 것처럼 보이므로, 두 변경을 하나의 트랜잭션으로 묶는다.

## 5. ACID 성질

ACID는 트랜잭션이 신뢰할 수 있게 동작하기 위해 기대하는 네 가지 성질의 약자다.

|성질|의미|계좌 이체 예시|
|---|---|---|
|**원자성(Atomicity)**|작업 전체가 성공하거나, 전체가 실패한다.|출금과 입금이 함께 반영되거나 둘 다 취소된다.|
|**일관성(Consistency)**|커밋 전후에 데이터 규칙을 만족한다.|잔액이 음수가 되지 않고, 계좌 제약 조건을 지킨다.|
|**고립성(Isolation)**|동시에 실행되는 트랜잭션이 서로의 중간 상태를 부당하게 보지 않는다.|다른 요청이 이체 중간의 임시 잔액을 읽지 않는다.|
|**지속성(Durability)**|커밋된 결과는 장애 뒤에도 유지된다.|성공 응답 뒤 서버가 꺼져도 이체 결과를 복구할 수 있다.|

> [!note] ACID는 “항상 공짜”가 아니다
> 강한 고립성과 복구 보장은 잠금, 로그, 복제 같은 비용을 수반한다. DBMS마다 고립성 수준과 구현 방식이 다르므로, 실제로는 필요한 정확성·성능·동시성의 균형을 설계해야 한다.

## 6. 송금으로 보는 전체 흐름

민지가 준호에게 10,000원을 이체하는 일을 단순화하면 다음과 같다.

1. DBMS가 트랜잭션을 시작한다.
2. 민지 계좌의 잔액과 계좌 상태를 읽고 출금 가능 여부를 검증한다.
3. 민지 잔액에서 10,000원을 뺀다.
4. 준호 잔액에 10,000원을 더한다.
5. 두 계좌의 규칙을 다시 확인한다.
6. 문제가 없으면 커밋하고, 하나라도 실패하면 두 변경을 롤백한다.

이 흐름에서 스키마와 제약 조건은 “어떤 계좌와 잔액이 유효한가”를 정의하고, 트랜잭션과 ACID는 “변경이 안전하게 끝났는가”를 보장한다.
